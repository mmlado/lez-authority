# The freeze slot is born with the config, and the admin appoints by nomination

The freeze slot lives in the program's config, so the admin's Init creates it with the config, with no freeze authority and nothing frozen, as the embedded mode of v0.2 bore its slot vacant. The freeze role has no Init. The admin appoints the first freeze authority by nominating it, and the nominee accepts, the same two steps that hand the role on later. That appointment meets RFP-002's requirement that a freeze authority can be set at program initialisation, as the born-vacant appointment of v0.2's embedded mode met it in v0.2's requirement matrix. Otherwise the lifecycle is that of v0.2: the freeze authority or the admin nominates (v0.2 ADR-0013), either of them renounces (v0.2 ADR-0004), and a renounce leaves the slot unset for the admin to fill again (v0.2 ADR-0007). Once the admin is renounced, the freeze authority keeps working, and a freeze slot that empties stays empty. A renounce changes only who holds the role, as in v0.2. A standing freeze and the frozen accounts stay until a freeze authority releases them, so an admin who revokes during an incident keeps the program frozen. The last authority releases before it renounces, or the freeze stays for good. The engine refused a nomination where a slot had no holder, so a slot gains a state for a standing offer with no holder yet, appended so that existing encodings stay.

## Considered options

- **A renounce that releases everything,** so a freeze never outlives its authority. An admin who revokes during an incident would lift the freeze until a new authority accepts and freezes again.
- **Refusing a renounce while the program is frozen.** Nothing is left frozen by accident, but the admin could not revoke during a freeze.
- **An Init of the freeze role that the admin sends,** installing the admin as the first freeze authority. One more operation and one more rule for who installs, beside the nomination that hands the role on anyway.
