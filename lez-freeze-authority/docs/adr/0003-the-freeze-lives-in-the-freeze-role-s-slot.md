# The freeze lives in the freeze role's slot, each frozen account at a marker

v0.2 kept the freeze authority and the program-wide flag on an account of their own, and each frozen account on another account of its own. On LEZ 0.4 a handler reads only the state of the actor it runs at, and the guard checks at the config. So the freeze authority and the flag live in the config, inside the freeze role's slot, next to the admin's. A program declares one field for the role, the way it declares the admin's slot, and each role names the type of its slot. The guard's check that a handler left every slot alone keeps the handler away from the freeze.

Each frozen account is marked at an actor of its own, its marker, as v0.2 kept one account per frozen account. The marker is the freeze role's own actor for the account's id (lez-authority ADR-0006), so the freeze's own messages, which only the config sends, run there and at no other actor. The config knows the caller of a message that came through the caller's seat, and of a request for clearance from an actor whose account authorized the transaction. It then asks the caller's marker in the same transaction, and the marker refuses while it holds the mark (E218). A private caller is asked under the id it presents, so a private account is refused only while it presents its real id. Any number of accounts can be frozen, and a frozen account makes no other account's messages dearer. A cap on a set of frozen accounts would not hold, since accounts are cheap to create and an attacker's fresh accounts would exhaust it. The price is one more execution for every freezable message with a caller, frozen or not, and a transaction that declares the caller's marker. The first check of each caller also registers its marker as an empty account.

A marker is a PDA of the program, and a program message reaches it like any other actor, since an open message runs wherever it is sent. So the freeze looks at the state around every handler (lez-authority ADR-0006). No handler runs at an actor that holds the mark (E227), and no handler writes a state that starts with it (E228). So only a freeze operation marks or unmarks an account. An account is frozen exactly while its marker holds the mark, and any other state there is stray. A freeze of an account writes the mark over whatever stray state sits at its marker, which any program message that reached the marker before the freeze could have put there, such as value sent to an address nobody holds. A release leaves the marker empty.

## Considered options

- **The frozen accounts in the config,** as a sorted set beside the flag, the way this crate first kept them. The per-account check costs no execution of its own, but each frozen account makes every message at the config and every clearance dearer. So the set needs a cap, and fresh accounts exhaust any cap.
- **A cap the admin sets,** with a default and a ceiling. The same exhaustion, and every message still pays for the set.
- **A mark at each frozen account's own seat,** the only actor where that account is ever a caller. No extra execution and no cap, but the state the program keeps at its actors would carry the mark. An id that never appeared on chain could not be marked ahead of time, since rc3 delivers to a public account only if it exists or the transaction carries its public key or PDA derivation. A private account could not be marked at all.
- **The flag and the frozen accounts in a second field** with an attribute of its own, next to an ordinary slot. The slot machinery would stay as it is, at the price of a second trait, a second attribute and a second check in the guard.
- **Refusing a freeze over stray state** at the marker. A credit of one token to one's own marker would then make an account unfreezable.
- **The markers in the engine,** behind one switch. Less for the freeze to carry, but the engine would decide what a role may do, where general hooks let each role build its own rules.
