# A message handled elsewhere asks the config for clearance

[ADR-0003](0003-roles-compose-through-traits.md) left open how a freeze gates ordinary messages. A freeze must reach a program message at any actor of the program, since an open message runs wherever it is sent ([ADR-0004](0004-the-guard-in-front-of-a-plain-handler.md)), but only the config holds the freeze. So when one of a program's roles requires it, the guard runs a program message at another actor as before, then adds a request for clearance, addressed to the config, to the handler's response. The config refuses it under that role's rules, and the whole transaction reverts, the handler's effects with it. A role requires it by setting `Policy::REFUSES_MESSAGES`, the same switch that has the config ask the role's `may_run`, so no role is enforced at the config alone. The request names no role, so a guard takes one such role at most and refuses a second at compile time. The handler sees its input exactly as it would without the role, so the program keeps its shape. The price is one more execution for each such message and a transaction that names the config actor. A private actor's request also adds its crossing to the transaction and runs at the config as a public segment. A refused message's handler runs before the refusal, and nothing it did survives. Until the root role's install, the config refuses every request for clearance, as it refuses every other message there, so nothing that asks for one runs anywhere before then. A request for clearance says only whether the sending actor's own account authorized the message, and the config takes that account from the sender, as it does for a hop. A private actor's call to the config runs at the sequencer as a public segment, where the runtime blinds the sender but not the body, so an account named in the body would publish a private caller.

## Considered options

- **The bounce.** The first actor forwards the message to the config, the config checks it and sends it back, and the handler runs at the first actor after the check. A refused handler never runs, but each such message costs two executions more, and the guard must hand the handler the original sender, carried through the hop. Otherwise the handler sees the config as the sender, and a message from any program passes the program's check that its sender is one of its own actors.
- **Running such messages at the config,** as a gated message runs. One execution more, but a program that keeps state at other actors, as LEZ's native token keeps each balance at its owner's actor, would run its handler against the config's state.
- **Refusing them,** so a program sends everything to the config and reaches its other actors through the hub. No new route, and the most rework for an integrator.
- **Checking only at the config.** Free, and a freeze with a side door: every message at another actor keeps running.
- **Granting clearance at an uninitialized config,** since an empty config freezes nothing. Messages away from the config would keep running before the install, as they do without the role, at the price of a case in the guard that answers without a config.
