# The freeze lives in the freeze role's slot

v0.2 kept the freeze authority and the program-wide flag on an account of their own, and each frozen account on another account of its own. On LEZ 0.4 a handler reads only the state of the actor it runs at, and the guard checks at the config. So the flag and the frozen accounts live in the config, inside the freeze role's slot, next to the admin's. A program declares one field for the role, marked as the admin's slot is, and each role names the type of its slot. The per-account check then costs no execution of its own, and the guard's check that a handler left every slot alone keeps the handler away from the freeze. Each frozen account adds its 32-byte id to the config, which every message at the config and every clearance reads. That suits incident response, which freezes a handful of accounts, and does not suit a long blocklist, which nothing on record asks for. So the frozen accounts have a fixed cap, set from a measurement so that a full set adds a small, stated cost to every message, and a freeze beyond it is refused (E226). A long blocklist is refused instead of making every message dearer.

## Considered options

- **A marker for each frozen account at an actor of its own,** as v0.2 kept one account per frozen account. The config stays small, but each per-account check becomes a second clearance, so every message with a caller pays one more execution and names the marker's actor. The guard would also have to keep program messages away from the markers, since an open message writes wherever it is sent.
- **The flag and the frozen accounts in a second field** with a marker of its own, next to an ordinary slot. The slot machinery would stay as it is, at the price of a second trait, a second marker and a second check in the guard.
- **No cap,** with the measured cost of each frozen account in the docs. A freeze authority that froze thousands of accounts would make every message dearer until it released them.
- **A cap each program sets,** with a default. A parameter on the slot type, for a need nothing on record states.
- **A mark at each frozen account's own seat,** the only actor where that account is ever a caller. No extra execution and no cap, but the state the program keeps at its actors would carry the mark, and the guard would decode that state before and after the handler at every seat. An id that never appeared on chain could not be marked ahead of time, since rc3 delivers to a public account only if it exists or the transaction carries its public key or PDA derivation.
