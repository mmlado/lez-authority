# The engine stands in layers that import downward

On LEZ 0.4 the engine took on the routing that SPEL gave a program on the SPEL-based v0.2 line, and the hooks that only a freeze uses, and both tangled with the primitives. `Policy` held the four holder rules and the hook items side by side, and the modules imported each other in cycles. So the engine now stands in five layers, each naming only those below it. lez-authority-core, in `core/`, holds what a role is, its slot and holder, the holder's four transitions, the init gate and the refusal table. It depends on borsh and `lee_core` alone, so the compiler keeps it from naming anything above it, as spel-authority was kept policy-free on that line. The table stays whole there, one enum and one list, so no code is used twice: the core raises the codes of its transitions and its holder check, and lists the others for the layers above. lez-authority holds the other four layers as modules, from the bottom `wire`, `policy`, `hooks` and `guard`. Each imports from the core and from the modules below it by path, never through the crate root. A test that reads their source fails on a path, an alias or a glob of the root, a member or a trait impl added to a lower type, or a doc link that reaches up, and on code it cannot read, such as an included file. What a macro from another crate generates is beyond it. The crate root re-exports every item, so a program sees one flat API. `Policy<C>` keeps who may install, nominate and renounce, and what renounce leaves. `Hooks<C>: Policy<C>` takes what a role adds to the guard: its consent, its own operations and messages, and its looks at state. So the admin reads as holder rules with an empty `Hooks`, and the freeze as holder rules and hooks.

This supersedes [lez-authority ADR-0003](0003-roles-compose-through-traits.md) where it gives a role's rules as `Policy<C>` alone. A role's rules are its `Policy<C>` and its `Hooks<C>`, and the guard requires both of every role.

The layers leave the hooks in the engine, used by the freeze alone, and the engine still decides what a role may do at each of them ([lez-authority ADR-0006](0006-roles-extend-the-guard-through-hooks.md)).

## Considered options

- **One read-only seam** at four steps of the guard, on which the freeze builds its consent, its clearance and its exemptions itself. It moves the freeze's rules out of the engine, but most of the code that only the freeze uses stays, and the guarantee that a role refusing at the config refuses wherever a program message runs ([lez-authority ADR-0005](0005-a-message-handled-elsewhere-asks-the-config-for-clearance.md)) becomes code in one role.
- **A registry program for the markers,** so the looks and the own message into the program go. It removes two hooks, and adds a second program to deploy and trust after every reset of the chain.
